# 候补与撤课反馈下的课程需求区间及复开选择

这是一个面向社区老年教育运营的本地分析原型，使用合成记录演示从业务记录到运营摘要的处理。项目把记录读取、统计口径和运营判断分开，便于核对原始事实与派生结果。

## 环境与使用

需要 Python 3.11 或更高版本，无第三方依赖。运行 `python3 -m unittest discover -s tests -v` 执行测试；运行 `python3 -m learning_waitlist_demand.report` 查看合成数据摘要。所有记录均为本地合成数据，不包含个人信息。
也可使用 Docker 运行：`docker build -t learning-waitlist-demand .`，再执行 `docker run --rm learning-waitlist-demand`。容器内运行测试可执行 `docker run --rm --entrypoint python3 learning-waitlist-demand -m unittest discover -s tests -v`。

## 数据

`data/courses.csv` 为课程静态属性（教师、时段、容量、最低成班人数）；`data/events.csv` 为带日期的事件流（开放、报名、候补、备选、退课、候补退出、停课、转班、放弃、意向登记）。SQLite 数据库在调用时创建于临时目录，原始 CSV 保持不变。

## 现有行为

可见选项与候补身份决定兼容偏好集合；联合需求分析决定开班保证；复开计划回查保留席位和教师互斥。

- 同一学员的正选与候补记录只汇聚为一人，不算作两个需求；报名时未展示（停课/未开放）的课程不解释为不喜欢；未留备选次序者不编造偏好。
- 每门课给出需求上下界：下界为确定需求（在册保留学位＋活跃候补与意向登记），上界另含可能需求（备选意向与停课后未确认的历史选择）。
- 联合需求用最大流检验哪些需求能同时成立，不把各课上界之和当成可兑现人群；课程的保证需求取"所有学员尽量避开该课"时的最小值。
- 复开方案检查教师时段互斥与最低成班人数，在办课程的保留学位不再承诺给候补者；每个方案列出可兑现学位（确定与乐观上限）、可能仍落空人数与证据缺口。数据支撑不了开班承诺时判"需补充意向"，不产出看似精确的预测数。
- 分析按截止日重放事件：候补退出、撤课转班、迟到的备选与意向登记只影响其发生之后的分析，不伪装成当时已知事实。

当前摘要只反映样例记录的基础汇总，不用于形成个体资格或运营承诺。
